# 日志按团队和岗位查询

状态：implemented
类型：feature
Owner：backend/package/yuxi/repositories/operation_log_repository.py

## 问题
管理员需要在操作日志和对话日志中按团队、岗位组合查询。

## 决策
团队对应用户当前部门，岗位对应当前角色（超级管理员、管理员、普通用户）。查询反映当前组织归属，用户调岗后历史日志随当前归属查询，不表示事件发生时的组织快照。

### 实现方案
两个日志页面通过已有部门 API 提供团队选项，并提供固定角色选项。路由校验正数部门 ID 和角色枚举，操作日志 repository 与 desktop conversation repository 在数据库分页及会话聚合之前应用条件，与员工、时间、操作类型或内容条件取交集。查询、刷新和分页沿用已应用条件，重置清空全部筛选。管理员权限沿用原接口依赖。

## 替代方案
新增团队、岗位模型与组织历史快照会扩大组织管理和迁移范围；当前需求明确复用现有部门和角色。

## 后果
不新增持久化字段。未分配部门的用户仍包含在全部团队查询中；选择具体团队后排除无部门用户。无效角色或非正数部门 ID 返回 422，不存在的正数部门 ID 返回空结果。

## 验证
HTTP/PostgreSQL 集成用例覆盖团队、角色、组合条件、冲突条件空结果及参数校验。组件用例覆盖条件提交、分页沿用和重置。相关组件测试 3 项、前端全量 lint、生产构建、相关 Python Ruff 检查通过。Docker 恢复后，真实 HTTP/PostgreSQL 日志集成测试 2 项通过，覆盖团队、角色、组合查询及无效参数；系统 readiness 返回 ready。线上对话日志部门筛选通过浏览器验证：全部部门 66 个会话，切换部门分别显示 1 个和 65 个会话，筛选后详情随会话切换。线上仅发布对话日志部门入口；操作日志与岗位入口仍属于本地实现。线上按现有资源增量更新页面模块，入口 import map 将旧主模块地址统一到新资源，防止缓存和循环依赖加载重复实例；后续完整构建可替代该增量发布。工程规范脚本因其他既有决策记录的 51 项格式问题失败，其自身 63 项单测通过。前端全量单测 415 项中 413 项通过；chatStartScreen 与 knowledge_evaluation_workspace 各有一项失败，涉及未在此功能修改的聊天布局和知识库导航。
